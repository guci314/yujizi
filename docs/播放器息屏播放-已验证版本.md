# 播放器息屏连续播放 —— 已验证可用的版本

**验证通过的真实设备**:小米 Android,Chrome。
**验证日期**:2026-10-03
**验证 commit**:`5c75dbb`(长亮锁改为自维持 + 意图轮询兜底)

## 结论

选「连续播放」+ 设「定时 1 小时」,息屏放置,音频不再中断。

根因是**息屏后系统暂停音频,而恢复路径有缺陷**,不是 JavaScript 被冻结。
用户截图里的日志是决定性证据:

```
17:52:37.651 [vis] pause-unattributed timer-active (paused)   ← 停止时是【可见】态
17:52:40.010 [hid] visibility hidden
17:55:22.858 [vis] visibility visible                          ← 回前台后什么都没发生
```

停止发生在可见态,且日志本身就是 JS 写的 —— 页面当时完全在运行。

真正起作用的改动是**屏幕长亮**(`navigator.wakeLock('screen')`):
直接让「息屏」这个触发条件不发生,而不是去防守息屏后的各种后果。

## 已知无效的部分

`js/keepalive.js` 里的 **Web Audio 静音导频**(18kHz @ −58dB)是猜错的方案,
从未被证明有效。用户实测成功的是长亮锁。这部分可以删掉 —— 它只白耗 CPU 和电。

调试面板里的 `keepalive-on` 字段会随之失效。

## 给未来的自己

1. **先消除触发条件,再考虑对抗它。** 遇到「只在息屏时坏」,最便宜的一招往往是让它不熄屏。
   静音导频(欺骗平台的「有声」判定)严格比直接长亮脆弱。
2. **桌面模拟不出手机行为。** CDP 的 `Page.setWebLifecycleState('frozen')`、
   headless 多标签的 `visibilityState` 都不是证据 —— 实测两个标签页都报 `visible`,
   `visibilitychange` 根本不派发。
3. **`visibilitychange` 在息屏期间不派发。** 所以唤醒锁丢了只能靠轮询找回,
   不能靠监听该事件。
4. **让用户用自己的证据说话。** 这次的决定性证据来自用户截图的 `visibilityState`,
   不是任何本地测量。
